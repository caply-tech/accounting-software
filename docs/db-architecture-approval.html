Summary

What's being proposed, in one paragraph, before the detail.

The application keeps two kinds of SQLite database: one shared core.db holding the business registry, user directory and installation settings, and one biz_<id>.db per business holding that business's ledger, payroll, inventory, assets and reports — matching the mockup's Multi-Branch/Company screen, which states each business's data is "completely separate and isolated." Every table uses a Drift-generated schema over SQLite, encrypted at rest with SQLCipher. Fields and relationships below are cited against the specific mockup screen that shows them. Three items originally flagged for a decision have since been confirmed: the Accounts & Finance and Asset & Valuation schemas stand as designed, the bank_reconciliations table has been added to the schema (§4), and LAN mode's key-sharing requirement is confirmed in scope (its exact mechanism is a Phase 3 implementation detail, not a schema question). One item remains open in §5.

The one mechanism the whole design turns on: which file a query can even reach, and where every module's writes end up funnelling.

02

Why two databases, not one

The Multi-Branch/Company screen (mockup page 3) states this requirement directly — the design below is what makes it literally true rather than convention.

The screen's "Independent & Isolated Businesses" panel reads: "Each business maintains independent financial, staff, inventory and administrative records. Data is completely separate and isolated between businesses." A single shared database with a business_id column on every table would satisfy that in spirit but not in practice — a missing or wrong WHERE business_id = ? clause becomes a silent cross-business data leak instead of a structural impossibility. Under this design, a wrong query can only ever see the one file that's open; there is no query that can accidentally join two businesses' ledgers.

A single point stays genuinely shared, and has to: the Sign In screen and the Multi-Branch selector both need to list businesses and authenticate users before any one business's file is chosen. That's what core.db exists for — nothing more than that registry and installation-wide settings.

03

Technology choices

Confirming the stack, not re-litigating it — this was decided in the earlier technology report; restated here for the reviewer of this specific approval.

ChoiceWhat it buys
SQLiteA single encrypted file per database, no server process, works identically offline on every Flutter target.
DriftTyped Dart tables/queries over SQLite (the classes in core_database.dart / business_database.dart) with generated migrations — no hand-written SQL strings scattered through the app.
SQLCipherTransparent AES-256 encryption at rest for both database files; key derived from the local master password, held in the OS credential store.
TEXT UUID keysEvery table's primary key is a client-generated UUID, not an autoincrement integer — keeps a future sync/merge feature (already named as optional in the architecture deck) from needing a primary-key migration.
Integer minor unitsEvery money column is INTEGER paise, never REAL — avoids float drift on repeated ledger arithmetic. UI divides by 100 and formats with ₹.

05

Confirmed decisions, and what's still open

Four points originally needed a call the mockup and architecture deck didn't fully settle. Three are now confirmed; one remains open.

Bank Reconciliation now has a backing tableConfirmed

The Reports screen lists "Bank Reconciliation" under Financial Reports and shows a completed "Bank Reconciliation Report" row in Recent Reports. bank_reconciliations (id, bank_account_id FK, statement_date, statement_balance, reconciled_balance, status) has been added to the schema and generated — see §4.

Accounts & Finance and Asset & Valuation schemas confirmedConfirmed

The 8-page mockup has no dedicated screen for either module, so their tables were originally inferred from standard double-entry/asset-register practice. Both schemas are now confirmed as final — no screen-level verification pending.

LAN key-sharing is a confirmed requirementConfirmed

The First-Run Setup screen's recommended "Local network (LAN)" mode means other devices connect to the host's live database, so the encryption key has to reach every connecting client, not only the device holding the file. This need is confirmed as in-scope; the specific key-sharing mechanism (e.g. a per-install key exchanged at first-run pairing, vs. a per-user key wrapping the database key) is a Phase 3 implementation detail to be designed when LAN mode is built, not a schema question blocking this approval.

Cross-file references aren't enforcedaudit_log.user_id

audit_log.user_id (and any "created/modified by" column in a business file) points at a row in core.db's users table — a different SQLite file. SQLite has no mechanism to enforce a foreign key across two separate database files, so this integrity is an application-code guarantee only; a bug could silently write an audit row for a user id that no longer exists.

Recommendation: accept this as a documented, tested application-level invariant, or duplicate a minimal user snapshot (id + username) into each business file at write time so the record is self-contained.

06

Security & integrity notes

  • Encryption at rest: both core.db and every biz_<id>.db are SQLCipher-encrypted; the key is derived from the local master password and never written to disk in the clear.
  • No binary data in SQLite: generated PDF/XLSX reports are filesystem artifacts referenced by file_path in generated_reports, not stored as BLOBs — keeps the encrypted file small and backups fast.
  • Double-entry integrity: a journal_entries row can only move from draft to posted once its journal_lines balance — enforced in application code before the status write, not by a database constraint.
  • Denormalized ledger: transactions is intentionally a write-through copy, not a view — recomputing the Dashboard/Reports feed with five live joins doesn't scale past a few thousand rows on laptop-class SQLite.
